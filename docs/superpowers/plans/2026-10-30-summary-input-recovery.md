# 요약 입력 보강과 누락 배치 복구

## 목표와 확인된 현상

28·29일 일간 HTML·JSON이 없고 마지막 게시 커밋은 27일분이다.
입력 선택 결함을 수정하고 누락된 두 날짜를 순서대로 재실행해 Git push와 기존 Slack 게시 결과를 확인한다.
30일 정기 실행은 아직 예정 시각 전이므로 복구 대상에 넣지 않는다.

| 시각(KST) | 관측 |
|---|---|
| 10월 28일 23:56 | 논문 선정 시작, 약 9초 후 성공 |
| 10월 29일 00:44 | 28일분 개발자 블로그의 필수 요약 누락으로 게시 전에 중단 |
| 10월 29일 23:56 | 29일분 논문 선정 시작 이후 실행 기록 단절. 종료 코드 미확인 |
| 10월 30일 조사 | HTML 478자(실제 글 14자)가 실제 본문 400자를 덮는 입력 결함 재현 |

## 원인과 한계

`main._analyze_items`는 HTML 요약과 일반 텍스트 본문을 문자열 길이로 비교한다.
태그가 긴 미리보기가 본문을 가리고, 요약 필수 여부의 150자 검사도 잘못 통과한다.
RSS 보강도 150자 이상 미리보기에는 원문을 가져오지 않는다.
28일 실패 입력 369자 자체는 보존되지 않아 이 결함이 해당 실패를 일으켰는지는 확정하지 않는다.
29일 기록 단절은 코드의 600초 제한 이전에 발생했으며 외부 종료 여부를 확인할 증거가 없다.

## 변경 흐름

| 단계 | 입력 → 처리 → 출력 | 변경 |
|---|---|---|
| RSS 수집 | 미리보기·피드 본문 → 1,500자 미만이면 제한된 수의 원문 조회 → 더 긴 본문만 보존 | 수정: `sources/rss.py` |
| 항목 분석 | HTML 요약·본문·초록 → 기존 `_plain_text`로 후보를 동일하게 정규화 → 가장 긴 일반 텍스트 | 수정: `main.py` |
| 필수 결과 검사 | Codex gpt-6.1-sol 응답 → 번역·요약 검증 → 정상 결과 또는 명시적 예외 | 기존 유지 |
| 일간 게시 | 검증된 결과 → HTML·JSON·주간·월간 저장 → Git 커밋·push·기존 Slack 게시 | 기존 유지 |

원문 보강 기준은 태그를 제거한 일반 텍스트 길이로 비교하며, 기존 인자에 선택 매개변수를 추가해 블로그 수집에만 1,500자를 적용한다.
커뮤니티의 기존 150자 보강 기준과 호출 제한·동시성·모델은 유지한다.
원문 조회가 실패하거나 기존 본문보다 짧으면 기존 값을 유지한다.
원문 보강은 기존 상한인 최대 40건, 동시 조회 8개, 요청당 10초를 유지한다.

## 재발 방지와 검증

- 테스트: HTML 속성으로 긴 요약이 실제 본문을 덮지 않는지, HTML 껍데기로 필수 요약 조건을 잘못 만족하지 않는지 검증한다.
- 테스트: 369자 미리보기의 원문 보강, 더 짧은 조회 결과 보존 금지, 조회 상한과 커뮤니티 기본 동작을 검증한다.
- 가드: 빈 필수 요약·번역과 비정상 응답은 계속 게시를 차단한다.
- 운영: `RUN_DATE`로 28일 이후 29일을 순차 실행하고 날짜별 stdout·stderr와 종료 코드를 `logs/`에 보관한다. 실패를 성공으로 보고하지 않는다.

## 복구 시 주의

RSS는 `RUN_DATE` 기준 최근 이틀 범위로 필터링한다. 현재 피드와 공개 API로 재수집하므로 당시 수집 결과 전체를 재현할 수는 없다. GitHub 트렌딩·arXiv는 현재 조회 결과이며 과거 순위를 복원한 것으로 보고하지 않는다.
날짜별 실행을 겹치지 않게 하고 이미 게시한 날짜는 다시 알리지 않는다. 게시 완료는 일간 파일 생성, Git push, Slack 응답의 각 단계로 구분해 로그를 확인한다. push 후 Slack만 실패하면 전체 배치를 다시 돌려 중복 게시하지 않는다.
각 날짜 실행 전에 활성 배치를 확인한다. 복구가 30일 정기 실행 시각까지 이어지면 동시 실행 여부를 확인하고 겹치는 새 실행을 시작하지 않는다.
필수 요약 실패를 숨기거나 불완전한 데이터를 강제로 게시하지 않는다.
